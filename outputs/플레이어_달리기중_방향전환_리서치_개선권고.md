# 달리기 중 방향 전환 — 현재 구조 분석 · 리서치 · 개선 권고

작성일 2026-08-02 / 브랜치 `dev/KBG-D` / **본 문서는 조사·권고서다. 코드·에셋·씬 수정 0건, 에디터 미접촉.**

요구사항: **"달리기 중 방향을 바꿔도 속도·포즈가 튀거나 리셋되지 않아야 한다."**

---

## 0. 결론 요약 (먼저 읽을 3줄)

1. **가장 큰 결함은 회전도, 블렌드 댐핑도 아니라 "입력 1프레임 공백 → Move→Idle→Move 왕복"이다.**
   키보드로 정반대 방향(W→S)을 누르면 Unity Input System의 2D Vector 컴포짓이 **정확히 `(0,0)`을 반환**한다(상하 상쇄). 그 순간 `LocoMoveState`가 Idle로 빠지고, 복귀 시 `_runCharge01`·`_animFloor`·`IsRunning`이 **전부 0으로 리셋**된다 → 목표속도 8 → 5로 떨어지고 다시 1초 램프. 사용자가 말한 "속도·포즈 리셋"의 직접 원인이다. **회전·블렌드를 아무리 튜닝해도 이건 안 고쳐진다.**
2. **입력이 끊기지 않는 경우(게임패드 스틱)의 방향 전환은 이미 상당히 잘 막혀 있다.** `_animFloor`(의도속도 상한 하한선)가 90°/180° 선회의 실속도 저하를 흡수한다. 다만 급반전 마찰 제동(`0.6`)이 걸리는 **~0.06초 구간에서만 애니(run)와 실속도(3.2m/s)가 어긋난다**.
3. **신규 pivot/turn 클립 없이 해결 가능하다.** 리서치의 정석(Lyra)은 pivot 클립을 쓰지만, 그건 "실속도 기반 블렌드"를 전제한 해법이다. 이 프로젝트는 이미 **의도(입력) 기반 하한**을 깔아 같은 문제를 클립 없이 우회하고 있고, 남은 결함은 전부 **상태 전이/타이밍 로직**이다. pivot 클립은 P3 폴리시 항목으로 남긴다.

### A-2. 입력 → 이동 방향

| 항목 | 실제 | 근거 |
|---|---|---|
| 바인딩 | `2DVector` 컴포짓, W/A/S/D, **모드 미지정 = DigitalNormalized(기본)**, 프로세서 없음 | `PlayerInputActions.inputactions` (Move 액션) |
| 컴포짓 산식 | `up(+1) + down(-1)`, `left(-1) + right(+1)`, 대각이면 ×0.707 | `DpadControl.MakeDpadVector()` (Input System 패키지 소스, `DpadControl.cs:123~142`) |
| 카메라 상대 변환 | `moveDirection = Quaternion.Euler(0, _moveBasisYaw, 0) * (x,0,y)` **후 `.normalized`** | `PlayerController.cs:1732` |
| 기준 yaw 래치 | 입력이 0이거나 **입력이 0.2 이상 바뀌면** 현재 카메라 yaw로 재래치 | `:1728`, 상수 `MoveBasisRelatchThresholdSqr = 0.04` `:405` |

> **핵심 함의 ①**: `.normalized` 때문에 **아날로그 세기가 소실**된다(스틱 30% 기울여도 100% 속도). 방향 전환 자체엔 무해하나, "살살 꺾기"가 불가능해 전환이 항상 최대 각속도로 일어난다.
> **핵심 함의 ②**: **W와 S를 동시에 누르면 입력이 정확히 `(0,0)`이다.** 키보드에서 180° 반전은 (a) 겹쳐 누르거나 (b) 떼고 누르거나 — 어느 쪽이든 **1~5프레임의 입력 공백**이 생긴다. 이게 §C의 V1이다.

### A-3. 속도 적용 — Rigidbody velocity 직접 대입 (관성 없음, 가속 램프 있음)

`DefaultMoveAbility.Move()` (`DefaultMoveAbility.cs:30~111`), **`Update`에서 호출**된다.

```
목표속도 = Lerp(walk 5, run 8, RunBlend01) × 버프배율 × (급반전이면 마찰제동)
새속도  = Vector2.MoveTowards(현재수평속도, 목표, accel × Time.deltaTime)
rb.linearVelocity = 새속도                                        :99~101
```

실제 값 (`PlayerCharacterData.asset`):

| 필드 | 값 | 비고 |
|---|---|---|
| `baseMoveSpeed` / `baseRunSpeed` | 5 / 8 | 걷기 = 0.625 속도비 (블렌드 임계값과 일치) |
| `runRampDuration` | 1.0 s | 이동 지속 시 걷기→달리기 램프 |
| `moveAccel` / `moveDecel` | 60 / 60 | 최근 커밋 `08801327d`에서 28→60 상향 |
| `reverseAccelMultiplier` | 1.75 | 역방향이면 accel ×1.75 = **105 m/s²** |
| `turnSpeedDegPerSec` | 720 | 회전 각속도 |
| `sharpTurnAngle` | 135 | 이 각도 이상이면 급반전 판정 |
| `sharpTurnMoveSlowdown` | **0 → 폴백 0.6 적용** | 에셋이 0이라 코드 상수 `DefaultSharpTurnBrake=0.6`이 쓰인다 |
| `initialBoost` | 0 | 출발 부스트 없음 |
| `groundDrag` | 4 | `Rigidbody.linearDamping`에 대입 `PlayerController.cs:1367` |

**방향 반전 시 velocity가 0을 지나는가 → 지난다.** `MoveTowards`는 속도 벡터 공간의 **직선**을 따라가므로 180° 반전은 원점을 통과한다. 8 → −8 (Δ16 m/s), accel 105 m/s² → **0.152초**, 그중 **0.076초 지점에서 |v|=0**.

부수적으로 `linearDamping=4`가 매 물리 스텝 속도를 ×0.926 감쇠시킨다. 8 m/s에서 스텝당 −0.59 m/s(≈29.6 m/s² 상당)를 accel이 매 프레임 되메우는 구조라 **정속 주행 중에도 실속도가 약 5% 리플**한다(추정치). `LocoMoveState.cs:79`의 주석이 지적한 그 리플이다.

### A-4. 회전 — 각속도 제한 슬루 + 목표 근처 ease-out

| 항목 | 실제 | 근거 |
|---|---|---|
| 방식 | 즉시 스냅 **아님**. `MoveTowardsAngle`로 각속도 제한 | `PlayerController.cs:1230` |
| 각속도 | 720°/s (에셋값), 폴백도 720 | `DefaultMoveAbility.cs:6, 109` |
| ease | **ease-out만.** 남은 각 40° 이하에서 `SmoothStep` 감속, 최저 배율 0.18 | `:1010~1011, 1229` |
| 적분 위치 | `FixedUpdate` → `Rigid.MoveRotation` (프레임률 독립) | `:1195, 1208~1233` |
| 권한 | `IsActionControllingFacing`(Act 상태 ≠ None/Pickup)이면 이동 회전 양보 | `:991`, `DefaultMoveAbility.cs:104` |

**180° 회전 실소요**: 140°는 전속 720°/s = 0.194s, 마지막 40°는 ease-out(평균 배율 ≈0.5) ≈ 0.11s → **합계 약 0.30초**. 즉 **회전(0.30s)이 속도 반전(0.15s)보다 2배 느리다** → 반전 직후 캐릭터는 **아직 뒤를 보는 채로 새 방향으로 이동**하는 구간이 ~0.15초 생긴다.

### A-5. 블렌드 파라미터 공급원 — **실속도 + 의도속도 하한 (하이브리드)**

`LocoMoveState.cs:76~87`:

```csharp
float actual01 = _controller.HorizontalSpeed01;                  // 실제 rb 수평속도 / runMax
_animFloor = moving ? Min(Max(_animFloor, actual01), IntendedSpeed01) : 0f;
float animSpeed = moving ? Max(actual01, _animFloor) : 0f;
SetSpeedParam(Anim, animSpeed);   // damp 가속 0.10 / 감속 0.08
```

- `HorizontalSpeed01` = **실물리 속도** 기반 (`PlayerController.cs:432~444`).
- `IntendedSpeed01` = **급반전 제동을 적용하기 *전*의 목표 속도비** (`DefaultMoveAbility.cs:74`). 제동 후가 아니라 **전** 값인 것이 의도적 설계다(제동을 애니가 따라가면 달리다 걷기로 튀므로).
- `_animFloor` = "이번 이동 중 도달한 최고 속도비"를 하한으로 깔되 `IntendedSpeed01`로 상한. **올라갈 땐 실속도 추종, 내려올 땐 붙잡는 비대칭 히스테리시스.**
- 이동 입력이 끊기면(`moving == false`) **하한이 즉시 0으로 리셋**된다 (`:85`).

즉 이 프로젝트는 **이미 "실속도 단독 구동"을 벗어나 있다.** 최근 커밋 `cdbf42f3e`("이동 블렌드에 의도 속도 하한 추가 — 달리는 중 Walk/Idle로 튀는 회귀 수정")가 정확히 이 문제를 겨냥했다.

## B. 리서치 — 게임들은 방향 전환을 어떻게 처리하는가

### B-1. 회전: 즉시 스냅 vs 각속도 제한

- **각속도 제한이 3D 액션의 표준.** Unreal `CharacterMovementComponent.RotationRate`가 "Orient Rotation to Movement"와 짝을 이루는 정식 파라미터이며, **음수 값을 주면 무한 각속도 = 즉시 회전**이 되도록 설계돼 있다 — 엔진 레벨에서 "스냅"을 각속도의 극단값으로 취급한다. 서드퍼슨 관용값은 **500~720°/s** 대역이다. ([Epic RotationRate](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/GameFramework/UCharacterMovementComponent/RotationRate), [Epic 포럼 — Orient Rotation to Movement](https://forums.unrealengine.com/t/orient-rotation-to-movement-issue/1659636))
- **탑다운·쿼터뷰는 스냅 쪽으로 기운다.** GDevelop의 탑다운 비헤이비어는 "rotate speed = 0이면 즉시 회전"을 기본 옵션으로 두고, Godot 레시피도 탑다운에서 회전 스무딩을 선택 사항으로 다룬다. 반응성 우선 장르(로그라이크/핵앤슬래시)일수록 회전 지연을 조작 지연으로 체감한다. ([GDevelop Top-Down](https://wiki.gdevelop.io/gdevelop5/behaviors/topdown/), [Godot Recipes — Top-down movement](https://kidscancode.org/godot_recipes/4.x/2d/topdown_movement/index.html))
- **트레이드오프 정리**: 각속도 제한은 "무게감"을 주지만 **회전이 끝나기 전에 이동이 시작되면 발-몸 방향 불일치(미끄러짐)**를 만든다. 즉 각속도를 낮출수록 pivot 클립 또는 방향 블렌드가 **필수가 된다**.

### B-2. 방향 반전 시 속도 처리

- 관용 해법은 **"방향은 즉시, 크기는 램프"**. 입력 방향을 목표로 삼고 가속으로 추격하되, 역방향일 때 가속을 배증하는 방식(현 프로젝트의 `reverseAccelMultiplier 1.75`가 정확히 이것)이 표준이다.
- **핵심은 "속도가 0을 지나는 것 자체를 막을 수는 없다"는 점**이다. 물리적으로 반전하려면 반드시 0을 통과한다. 그래서 업계 해법은 **속도를 손보는 게 아니라 "애니메이션이 그 0을 보지 않게 하는 것"**으로 간다 → B-3.

### B-3. 애니 블렌드를 물리 속도와 분리하기 — **가장 직접적인 정답**

- **Lyra(UE5)의 명시적 설계 원칙**: pivot 판정에 **가속도(= 입력 의도)를 쓰고 속도를 쓰지 않는다.** 원문 요지 — *"Acceleration communicates player intent better for that purpose than velocity does."* pivot 전이 조건은 **`dot(velocity, acceleration) < 0`**, 즉 "가려는 방향과 실제 가는 방향이 반대"일 때다. ([Lyra Breakdown — Game Core Animation](https://www.jaydengames.com/posts/ue5-black-magic-game-core-animation/), [Epic — Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine))
- **왜 실 velocity로 구동하면 안 되는가** (리서치가 공통으로 드는 이유):
  1. 방향 전환 시 크기가 물리적으로 붕괴한다(90°에서 0.707, 180°에서 0).
  2. **벽/적 충돌** 시 velocity가 0인데 입력은 계속 들어옴 → 애니가 Idle로 떨어졌다가 벽에서 떨어지면 다시 Run으로 튄다.
  3. 드래그/마찰/넉백 잔여 속도 등 **의도와 무관한 성분**이 섞인다.
  4. 프레임 단위 리플이 블렌드 임계값 근처에서 떨림(chatter)을 만든다 — 그래서 raw velocity 대신 **스무딩된 파라미터**를 넣으라는 조언이 반복된다. ([MoCap Online — Blend Tree 가이드](https://mocaponline.com/blogs/mocap-news/animation-blend-tree))
- **반대 리스크(공정하게)**: 의도 속도로만 구동하면 **벽에 붙어 제자리 달리기**가 나오고, 감속 잔여 속도 구간에서 발이 끌린다. 그래서 실무 해법은 **"의도를 하한, 실속도를 상한 근처"로 섞는 하이브리드** — 현 프로젝트의 `_animFloor`가 이미 이 형태다.

### B-4. pivot / turn 클립을 쓰는 게임 vs 안 쓰는 게임

| 진영 | 방식 | 대표 |
|---|---|---|
| **쓴다** | 급반전 감지 → 전용 pivot 클립 재생 + Distance Matching으로 재생속도를 실이동거리에 동기화 + Orientation/Stride Warping으로 잔여 오차 보정 | Lyra/UE5 표준, 라스트 오브 어스·갓 오브 워 계열 3인칭 시네마틱 액션 ([Epic — Distance Matching](https://dev.epicgames.com/documentation/unreal-engine/distance-matching-in-unreal-engine), [Epic Tech Blog — Adapting Lyra animation](https://www.unrealengine.com/en-US/tech-blog/adapting-lyra-animation-to-your-ue5-game)) |
| **안 쓴다** | 빠른 스냅/고각속도 회전 + 안정적인 1D 속도 블렌드. 카메라가 멀어 몸 회전의 디테일이 안 보이는 것을 이용 | 탑다운·쿼터뷰 로그라이크 일반. 회전 0.2~0.3초는 원거리 카메라에서 판별되지 않는다 |

- Turn-in-place는 **정지 상태에서 시선만 도는 상황**용이며(Lyra는 yaw 오프셋 50° 초과 시 발동), **달리기 중 방향 전환과는 별개 문제**다. 달리기 중 전환은 pivot 또는 방향 블렌드가 담당한다.
- **로그라이크·탑다운의 실용적 선택**: 클립 제작비(180°/L90/R90 × 무기별)를 감안하면 **"회전 각속도를 충분히 높게 + 블렌드를 의도 기반으로 안정화"**가 비용 대비 효과가 압도적이다. pivot 클립은 카메라가 가까운 컷신/보스 연출에서 값어치가 생긴다.

### B-5. 8방향/자유 방향 이동에서의 방향 전환

| 방식 | 거동 | 비용 |
|---|---|---|
| **2D 방향 블렌드**(Speed×Direction, 캐릭터는 카메라/조준 기준 고정) | 전환이 **포즈 공간에서 연속적** — 몸을 돌리지 않고 스트레이프. 전환 튐이 구조적으로 없음 | 클립 4~8종 × 속도단계. Unity 2D Freeform Directional 필요 ([Unity — 2D Blending](https://docs.unity3d.com/Manual/BlendTree-2DBlending.html)) |
| **이동방향으로 회전 + 1D 속도 블렌드** ← **현 프로젝트** | 포즈는 항상 "전방 이동" 1종. 전환은 **몸 회전으로만 표현**되고, 회전이 늦으면 옆/뒤로 미끄러짐 | 클립 3종으로 끝. 가장 저렴 |

현 프로젝트 방식의 구조적 한계는 **"전환의 시각적 표현 수단이 회전 하나뿐"**이라는 점이다. 따라서 **회전이 느려지면 곧바로 미끄러짐으로 보인다** → 이 구조를 유지하는 한 **회전 각속도를 낮추는 방향의 튜닝은 금물**이다.

## C. 대조표 — 현재 구조 ↔ 베스트 프랙티스

| 축 | 현재 (근거) | 베스트 프랙티스 | 판정 |
|---|---|---|---|
| **회전 방식** | 각속도 제한 720°/s + 목표 40° 이내 ease-out, FixedUpdate 적분 | 서드퍼슨 500~720°/s, 탑다운은 더 빠르거나 스냅 | ✅ **적정**. 값·적분 위치 모두 정석. ease-out 유무만 취향 |

| **블렌드 공급원** | `max(실속도, 의도속도 하한)` 하이브리드 | 의도(가속도/입력) 우선, 실속도는 보정 | ✅ **방향은 정답.** 단 하한이 `moving`에 종속돼 입력 공백에 붕괴 |
| **하한의 상한값** | `IntendedSpeed01` = **제동 적용 전** 값 | — | ⚠️ 의도적 선택이나, 제동 구간(0.06s)에 **애니 8m/s vs 실제 3.2m/s** 불일치 발생 |
| **pivot / turn 클립** | 없음 | Lyra: pivot + Distance Matching. 탑다운: 생략이 일반적 | ✅ **생략 타당**. 단 회전이 느려지면 즉시 결손이 된다 |
| **방향 블렌드 축** | 1D(속도만) | 2D(속도×방향)면 전환이 포즈로 표현됨 | ➖ 장르상 허용. P3 폴리시 |
| **입력 공백 처리** | 없음. 1프레임 0 입력 → Idle 전이 + 전체 리셋 | 입력 유예(coyote)·상태 유지가 관용 | ❌ **최대 결함** |

### V1 ❌ 입력 1프레임 공백에 로코모션 상태가 통째로 리셋된다 — **[신규] 최우선**

**증상**: 달리는 중 방향을 반대로 바꾸면 속도가 8→5로 떨어지고 다시 1초에 걸쳐 차오른다. 포즈도 Run→Walk로 내려갔다 올라온다.

**메커니즘** (전부 코드 근거):
1. 키보드 W→S 전환 시 두 키가 겹치는 동안 컴포짓이 `(0,0)` 반환 (`DpadControl.cs:125~130`: `1 + (-1) = 0`). 떼고 누르는 경우에도 인간의 손가락 간격 30~80ms = **2~5프레임 공백**.
2. `LocoMoveState.Update:45` → `moving == false` → `:85` **`_animFloor = 0`**, `:64` **`_runCharge01 = 0`**, `:98` **`Change(LocoState.Idle)`**.
3. `LocoIdleState.Enter` → `:19` `CrossFadeInFixedTime("MoveBlend", 0.14)`, `:21` `SetSpeedParam(0)`, `:24~25` **`IsRunning = false`, `ClearRunAfterDash()`**.
4. 다음 프레임 입력 복귀 → `LocoIdleState:48` → `Move` 재진입 → `LocoMoveState.Enter:35~39` **`_runCharge01 = 0`, `_animFloor = 0`** + 또 한 번 `CrossFade`.
5. 결과: `RunBlend01 = 0` → `DefaultMoveAbility.cs:66` **목표속도 8 → 5**. 다시 `runRampDuration 1.0`초 램프.

**권고 R1 — 이동 입력 유예(coyote) 창 도입** · 우선순위 **P0** · 난이도 **하** · **[신규]**

- `LocoMoveState`가 `moving == false`가 되어도 **즉시 Idle로 가지 않고 0.10~0.15초 유예**한다. 유예 중에는 `_runCharge01`·`_animFloor`를 **유지**하고, 이동은 `Move(Vector3.zero)`(정지 램프)로 자연 감속시킨다.
- 유예 안에 입력이 돌아오면 상태 전이 자체가 없으므로 **리셋·CrossFade 왕복이 통째로 사라진다.**
- 값 근거: 반전 시 velocity가 0을 지나는 시간이 0.152초이므로 유예 0.12초면 "키보드 반전"은 덮고 "진짜 정지"는 0.12초만 늦어진다(정지 자체는 유예 중에도 감속 램프가 돌아 시각적 지연 없음).
- **대안(더 작은 변경)**: 유예를 `LocoMoveState`에 두지 않고, `_runCharge01`을 `PlayerController`로 승격해 **"Idle 진입 후 0.2초 안에 Move로 복귀하면 charge를 복원"**. 상태 전이는 그대로 두고 리셋만 막는다. 리스크 최소.
- **추천**: 첫 번째(유예 창). 이유 — CrossFade 왕복·`SetSpeedParam(0)`·`IsRunning` 토글까지 한 번에 없앤다.

**권고 R1b — 입력 레이어에서 상쇄 자체를 없앤다(선택)** · 우선순위 **P1** · 난이도 **하** · **[신규]**

- W+S 동시 입력이 0이 되는 것은 컴포짓 기본 동작이다. "마지막에 누른 키 우선(SOCD last-input-wins)" 처리를 `CheckMovementInput` 앞단에 넣으면 **겹쳐 누르는 케이스의 공백이 원천 제거**된다.

### V2 ⚠️ 급반전 제동 구간에서 애니(run)와 실속도(3.2m/s)가 어긋난다 — **[신규]**

| 안 | 변경 | 효과 | 리스크 |
|---|---|---|---|
| **R2-a (추천)** | `sharpTurnMoveSlowdown`을 에셋에 **0.25~0.3** 명시 (현재 0 → 폴백 0.6) | 반전 직후 목표 5.6~6 m/s. 애니(8)와의 괴리가 절반 이하. 조작 씹힘도 감소 | 무게감 감소 — 의도된 연출이었다면 되돌리기 |

### V3 ⚠️ 회전(0.30s)이 속도 반전(0.15s)보다 느려 미끄러지는 구간이 생긴다 — **[중복 일부]**

**메커니즘**: `FacingSlewEaseOutAngle = 40°` + `FacingSlewEaseFloor = 0.18` (`PlayerController.cs:1010~1011`) 때문에 마지막 40°가 전속의 18~100%로 감속된다. 큰 회전일수록 이 꼬리가 비중을 키운다.

**권고 R3 — 큰 회전에서는 ease-out 구간을 좁힌다** · 우선순위 **P1** · 난이도 **하** · **[중복: 회전 관련은 병렬 태스크의 결함 G에 등재됨 — 단 그쪽 해법은 "헤드 룩앳 IK"로, 각속도 자체는 손대지 않는다]**

- ease-out은 **짧은 회전(코너 다듬기)에 유효**하고 180° 반전에서는 순손실이다. `remaining`이 90°를 넘는 동안은 ease를 1.0로 고정하고, 40° 이하에서만 감속하도록 조건을 좁히면 180° 회전이 **0.30s → 0.25s**로 줄어 속도 반전(0.15s)과의 격차가 준다.
- **각속도 720°/s 자체는 건드리지 말 것.** §B-5에서 정리했듯 이 구조는 전환의 시각 표현이 회전뿐이라, 각속도를 낮추면 즉시 미끄러짐으로 보인다.
- 대안: `turnSpeedDegPerSec`를 900~1080으로 올리면 180° 회전이 0.20s가 되어 속도 반전보다 빨라진다. 다만 "휙 도는" 인상이 강해지므로 **R3(ease 축소) → 부족하면 각속도 상향** 순서를 권한다.

### V4 ⚠️ 하한(`_animFloor`)이 "지금 이동 중"에만 유효해 벽 충돌에도 붕괴한다 — **[신규]**

`_animFloor`는 `moving`(=입력 유무)에만 종속되므로 입력이 살아 있는 한 벽 충돌은 잘 방어된다. **다만 V1의 입력 공백과 결합하면 "벽에 부딪혀 미끄러지며 방향 전환" 같은 복합 상황에서 무너진다.** R1이 해결되면 이 축도 함께 닫힌다. **별도 조치 불필요 — R1에 흡수.**

### V5 ➖ 1D 블렌드라 전환의 시각적 표현이 회전 하나뿐 — **[중복]**

병렬 태스크 계획서의 **G'(2D Freeform 교체, P3)**과 동일 항목. 이 조사도 같은 결론이다: **달리기 중 방향 전환 문제 해결에 2D 블렌드는 불필요**하다. R1~R3로 충분하며, 2D는 "스트레이프/조준 이동"이라는 **다른 기능**을 열 때 착수할 항목이다. **지금 착수 권장하지 않음.**

### V6 ➖ 물리 쓰기가 `Update`에 있다 — **[신규] 낮은 우선순위**

`LocoMoveState.Update` → `Move()` → `rb.linearVelocity` 대입이 `Update`에서 일어난다(`PlayerController.cs:1174`). 회전은 이미 `FixedUpdate`로 옮겨져 있는데(`ApplyFacing`) 속도는 남아 있다. `linearDamping 4`와 겹쳐 정속 주행 중 약 5% 리플이 생긴다.

**권고 R6** · 우선순위 **P2** · 난이도 **중** · **[신규]** — 속도 적분도 `FixedUpdate`로 이관하거나, `groundDrag`를 0으로 두고 감속을 `moveDecel` 단독으로 처리해 **감쇠 소스를 하나로 통일**한다. 방향 전환 튐과의 직접 인과는 약하므로 **R1~R3 검증 후에 착수**. 값 튜닝이 광범위하게 재조정돼야 하므로 리스크 중.

## E. 부수 관찰 (범위 밖 — 수정 권고 아님, 기록만)

1. **`MoveScale`의 부분값이 이동 속도에 반영되지 않는다.** `LocoMoveState.cs:44`가 `MoveDirection * MoveScale`을 넘기지만 `DefaultMoveAbility.cs:51`에서 `direction.normalized`로 크기가 소실된다. 결과적으로 `MoveScale`은 **0(정지) 또는 1(정상)로만 동작**한다. 현재 호출부는 전부 0/1이라(스킬 이동 잠금) 실害는 없으나, `PlayerController.ApplySlow(scale, duration)`(`:479`)은 **호출부가 없고 있어도 무효**다. 슬로우 디버프를 넣을 때 발이 걸린다.
2. **아날로그 입력 세기 소실**: `:1732`의 `.normalized`로 게임패드 스틱의 기울기 정도가 무시된다. 걷기/달리기를 스틱 세기로 나누려면 이 지점이 손봐야 할 곳이다.
3. **`CrossFadeInFixedTime`을 이미 재생 중인 동일 상태(`MoveBlend`)로 호출했을 때 사이클 위상이 리셋되는지는 확인하지 못했다.** Unity 문서는 `fixedTimeOffset`이 목적 상태의 시작 시각을 정한다고만 명시하고, 동일 상태 재진입 동작은 커뮤니티 보고가 엇갈린다. **R1을 넣으면 Idle↔Move 왕복 자체가 사라지므로 이 질문은 무의미해진다** — 별도 조사 불필요. ([Unity — Animator.CrossFadeInFixedTime](https://docs.unity3d.com/ScriptReference/Animator.CrossFadeInFixedTime.html))
