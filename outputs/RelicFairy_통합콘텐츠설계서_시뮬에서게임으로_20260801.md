# 1. 진단 요약 — 왜 "시뮬레이션"처럼 느껴지는가

## 1-1. 방 구조 6대 원인 (진단서 §0 인용)

| # | 진단 | 근거 |
|---|---|---|
| **A** | **플레이어 선택이 미래를 바꾸지 않는다** (경로 독립) | `RunSequencer.cs:168` `new Random(Combine(_seed, _visitCount))`. 주석: *"어느 문을 커밋해도 다음 깊이 종류가 동일"* |
| **B** | **런의 절반이 선택지 없는 일직선 복도** | Shop/Crucible/Refinery/PreBoss/비전투Event의 `grid_csv`에 출구 DR이 1개뿐 → Ch1 11방 중 갈림길은 4~5개, 전부 전반부 |
| **C** | **특수방을 한 번 안 고르면 챕터 내내 영구 소실** | `RunSequencer.cs:175-176` `NoteForcedSpecial()`이 **문을 굴리는 시점**에 캡을 소진. 플레이어가 안 골라도 `_shopUsed=1` |
| **D** | **챕터 내부 난이도 곡선이 무력** | 몹 스탯은 `ChapterDataSO.difficultyScale` 챕터 상수뿐. 템플릿 선택창(±0.35)은 **Ch2~4 Elite 전 구간 0/4 미스** → 균등 추첨 |
| **E** | **보스 직전 4연속 비전투** | 마일스톤 `4:Shop\|5:Event\|6:Crucible\|7:Refinery`, Ch1 boss@8 |
| **F** | **정예방이 순수 손해** | `RoomClearGate.cs:122-129` Normal/Elite 동일 경로. rarity floor·개수 보너스 **없음**. 몹은 32 vs 28 |

**+ 부수(진단서 §4-G)**: 시작방 매 런 동일 / 보물·휴식·치유방 타입 부재 / `sanctum` 이벤트는 상호작용 없이 즉시 클리어 / Ch4 38방 사장(`_finalChapter=Chapter3`) / 같은 티어 방들의 **스포너 토큰이 전부 동일**(Ch1 전투는 실질 2가지).

## 1-2. 그 위에 얹히는 3개의 구조적 공백

진단서는 **런 내부**만 봤다. "시뮬레이션 느낌"의 나머지 절반은 **런 바깥**에 있다.

### ① 죽음에 의미가 없다 — 메타가 "선택지"가 아니라 "능력치"다

코드 실측 결과 현재 영구 성장은 **6종 스탯 각성 하나뿐**이다.

```
UserGameData.awakeningLevel { Sword, Shield, Heart, Step, Mana, Luck }  ← 전부 수치
해금 목록(무기/유물/서약/룬/시작보너스) 필드 = 없음
```

이는 `리뷰/meta-progression-design.md` §0-2의 황금률
> *"해금 = 난이도 하락이 아니라 **선택지 확장**(adds options, not power). 영구 파워 인플레는 런 내 선택의 무게를 죽인다"*

와 **정면으로 반대**다. 지금 구조에서 100판을 해도 늘어나는 건 **숫자뿐이고 게임은 그대로**다. 다음 런이 "새로워지는" 경로가 데이터상 존재하지 않는다.

### ② 런에 목표가 없다 — 진행이 보이지 않는다

`RunSequencer`는 런 시작 시 `BuildPlan()`으로 **보스까지 전 깊이를 이미 알고 있는데**, 플레이어에게 노출되는 것은 다음 방 2개의 종류 라벨(`ExitCompassHud`)뿐이다.

- "보스까지 몇 방 남았는지" 화면에 없다
- "이번 런에서 뭘 노리는지"(목표)가 없다
- → 세션을 끊을 때 **재개할 이유(Ovsiankina)** 가 생기지 않는다

세이브·이어하기는 **이미 구현돼 있다**(`LocalFileRunSaveStore`). 즉 지금 부족한 건 기능이 아니라 **동기 노출**이다.

### ③ 도파민이 "방 안"에만 있고 "방 사이"에는 없다

진단서 §5-2 도파민 지도:

```
강한 지점:  룬 3지선다 · 보스 파츠 드래프트 · 재련소 도박
약한 지점:  문 선택(A·F) · 정예 클리어(보상 동일) · 원석 +4(소비처를 못 만날 수 있음)
빈 지점:    방 자체의 서프라이즈(보물방 없음) · 방 진입 전 정보 · 방 크기/구조 대비
```

**플레이어가 느끼는 선택의 90%가 방 안에서 일어나고, 방 구조(어디로 갈까)에서는 거의 일어나지 않는다.** 그래서 방과 방 사이가 "진행 처리"처럼 느껴진다 — 이게 "시뮬레이션 감각"의 정체다.

## 1-3. 한 줄 진단

> **RelicFairy는 "빌드를 조립하는 시스템"은 잘 만들어져 있고, "그 빌드를 걸고 도박하게 만드는 구조"가 비어 있다.**
> 리스크가 없으니 리워드가 안 짜릿하고, 해금이 없으니 죽음이 안 아프고, 목표가 없으니 이어할 이유가 없다.

# 2. 세 개의 루프 설계

게임은 **세 개의 시간 축**을 동시에 굴려야 "게임"이 된다.

```
┌─ 런 사이 (메타)  ──── 죽어도 다음 런이 "달라진다"       ← §2-1  현재 = 스탯 6종뿐 ❌
│
├─ 런 내부 (도파민) ─── 이번 런이 "터진다"                 ← §2-2  현재 = 방 안에만 있음 △
│
└─ 세션 사이 (복귀) ─── 껐다 켜도 "이어서 하고 싶다"        ← §2-3  현재 = 노출 없음 ❌
```

---

## 2-1. 런 사이 메타 — 해금·영구 성장

### 원칙 (meta-progression-design.md §4 가드레일 준수)

> **파워형 금지, 선택지 확장형 메인 + 내러티브형 보조.**
> 새 해금은 *강해지는 것*이 아니라 *새로운 판이 열리는 것*이어야 한다.

7개 체크리스트(원문 §4)를 본 설계에 그대로 적용한다:
① 파워 아닌 옵션 추가 / ② 런 내 선택 무게 유지 / ③ 그라인드 게이팅 없음 / ④ 통화가 플레이에서 자연 발생 / ⑤ 도전이 파워 없이 재공급(서약) / ⑥ 패배가 진전으로 프레이밍 / ⑦ 다음 목표가 세션 종료 시점에 노출.

### 재화 정합 — 신규 재화 0

이미 확정된 4종 경제(v0.2 §7-1)를 **그대로 쓴다.**

| 재화 | 스코프 | 소비처 | 상태 |
|---|---|---|---|
| 골드 | 런 | 상점 | 구현됨 |
| 강화재료 | 런 | 재련소 | `FuelKind.EnhanceMaterial` 구현됨 |
| 원석 | 런 | 정제소 | `FuelKind.RuneOre` 구현됨 |
| **유물 코어(`abyssEssence`)** | **메타 영구** | **각성 + ★신규 해금 트리** | 필드 존재, 소비처가 각성뿐 |

→ **메타 통화를 새로 만들지 않는다.** `abyssEssence`의 소비처를 "스탯 6종"에서 **"스탯 + 해금 트리"** 로 넓히는 것이 전부다. 미소비 연료의 메타 환산(v0.2 §6-2 "로스 0")도 이미 설계돼 있다.

### 해금 트리 5갈래 (베이스캠프 = 무대)

베이스캠프에는 이미 거점 오브젝트가 서 있다 — `RelicAltar`(유물) / `WeaponForgeAltar`(무기 모루) / `CovenantPickup`(서약) / `WorldAwakeningAltar`(각성). **해금 트리는 새 방을 만드는 게 아니라, 이 4개 제단에 "잠긴 슬롯"을 붙이는 것**이다.

| 갈래 | 해금 대상 | 거점 | 선택지 확장인가? | 기존 자산 |
|---|---|---|---|---|
| **① 무기** | 무기 타입(대검·활·석궁…) + 진화 분기 | `WeaponForgeAltar` | ✅ 새 무브셋 = 새 플레이 | `WeaponEvolutionSO`(**미배선**, 호출처 0건 — 재련소 기획 §3.2) |
| **② 유물** | 유물(가웨인·랜슬롯 → 갈라하드…) + **코어 파츠 풀** | `RelicAltar` | ✅ 새 아이덴티티 메커니즘 | 유물성장 설계 §8 파츠 표 |
| **③ 서약** | 원인/효과 **조각** 팔레트 | `CovenantPickup`/조립대 | ✅ 조합 공간 확장(원인24×효과31) | 유물성장 설계 §3 팔레트 |
| **④ 룬** | 속성 존 / 특수 룬(존핵·공명석) 종류 | 정제소(런 내) + 베이스캠프 도감 | ✅ 굴림 풀 확장 | 정제소 속성응축 §3 |
| **⑤ 시작 보너스** | 런 시작 조건(시작 강화재료 / 시작 룬 1개 / 첫 상점 할인 / 서약 1개 선지급) | `WorldAwakeningAltar` 확장 | ⚠️ **파워형 위험 구간** | — |

> ⚠️ **⑤만 파워형이다.** 그래서 ⑤는 **"양이 아니라 시작 스타일"** 로 설계한다 — "공격력 +5%" 같은 항목을 넣지 않는다. 대신 *"강화재료 8개를 들고 시작(재련소를 일찍 굴린다)"*, *"서약 1개를 미리 갖고 시작(대신 챕터1 서약 획득 없음)"* 처럼 **런의 시작 형태를 바꾸는 트레이드오프**로만 구성한다. 기존 6종 스탯 각성은 그대로 두되, **추가 확장은 하지 않는다**(인플레 동결).

### 죽음의 재프레이밍 — Hades식 4대 장치 (meta-progression-design.md §0-3)

| 장치 | RelicFairy 구현 |
|---|---|
| **메타 통화** | 런 종료 시 `GainedEssence` + **미소비 연료 환산** → 결과 화면에서 **숫자가 올라가는 연출** |
| **내러티브 진행** | 멀린 미스터리(v0.2 §1) — 죽을 때마다 실마리 1조각. 해금 항목에 로어 텍스트 첨부 |
| **다음 해금 노출** | 결과 화면 하단에 **"다음 해금까지 코어 12개 남음 — [무기: 대검]"** 고정 표시 ★핵심 |
| **No Game Over** | "GAME OVER" 문구 금지. **"영혼이 돌아왔다 — 심연 도달 깊이 7"** 로 프레이밍 |

### 이 루프가 만드는 것

```
1회차 런: 무형검 · 가웨인 · 서약 프리셋 3택 · 6속성 균등
    ↓ 죽음 → 코어 14 획득 → [대검] 해금
5회차 런: 대검 시작 가능 → 무브셋 다름 → 룬 빌드 방향도 다름
    ↓ … → [랜슬롯] [원인:벼랑끝] [정제소 공명석] 해금
20회차 런: 조립 가능한 조합이 처음의 5배 → "이번엔 저걸 해볼까"
```

**해금이 파워가 아니라 "해보고 싶은 것"의 목록이기 때문에, 20회차가 1회차보다 쉬워지지 않으면서 더 재미있다.**

## 2-2. 런 내 도파민 — 랜덤·상승감

### 설계 원칙 3가지

1. **같은 자극을 두 번 주지 않는다** (재련소·정제소 기획 §0) — 재련소는 **겁을 주고**, 정제소는 **홀린다**. 방마다 도파민 성격이 달라야 한다.
2. **바닥은 안전, 천장은 열려 있다** (v0.2 §6-1) — 전투방 = 높은 바닥(보장), 이벤트/정예 = 높은 천장(리스크가 바닥을 깎음).
3. **연출 강도는 등급에 비례** (정제소 §7) — 소형은 배너+대사, 대형(금테)만 `VolumePulse`/`HitFeel.Heavy`까지.

### ① 보상 선택 강화 — "3지선다"를 계층화

현재 전투방 클리어는 **어떤 방이든 룬 3지선다 + 원석 4 고정**이다. 여기에 **차등**을 넣는다.

| 방 | 후보 수 | rarity floor | 연료 | 추가 |
|---|---|---|---|---|
| Normal 하위티어 | 3 | 없음 | 원석 4 | — |
| Normal 상위티어 | 3 | 없음 | 원석 4 | — |
| **Elite** | **4** | **Rare 이상 확정** | **원석 6 + 강화재료 2** | **선택 후 1개 추가 리롤권** |
| 이벤트 챌린지 | 등급별 | 등급별 | 등급별 | (이미 구현) |
| **보물방(신규)** | 3 | **Epic 이상 확정** | — | 전투 없음, 대신 **대가 지불**(HP/저주) |

> **재사용:** `RollRewardChoices(count, rarityFloor)` 오버로드와 `ChallengeRewardTable.DefaultReward(grade, chapter, isInteraction)`가 **이미 챌린지 경로에서 동작 중**이다. 일반 클리어 경로(`RoomClearGate.cs` else 분기)에 `RoomPlanKind`를 전달하는 것만으로 위 표가 성립한다. → **P0에서 가장 싼 항목.**

### ② 희귀도 연출 — 등급이 "보여야" 도파민이 된다

정제소 설계 §7의 색·연출 체계를 **런 전체의 공통 언어로 승격**한다.

| 등급 | 색 | 연출 강도 |
|---|---|---|
| Common | 회 | 없음 |
| Rare | **청** | 프레임 플래시 + 가벼운 착지음 |
| Epic | **자** | 프레임 발광 + 약한 펄스 |
| Legendary | **금** | 강발광 + `VolumePulse.Pulse` + 팡파레 + **시간 살짝 감속** |

이 색은 **룬 보상 카드 / 정제소 리빌 / 상점 진열 / 문 위 보상 프리뷰 / HUD 버프창** 전부에서 동일해야 한다(§4-2).

### ③ 빌드 폭발 순간 — "지금 강해졌다"를 알린다

현재 시너지 단계가 올라도 **화면에 아무 일도 안 일어난다**. 유능감(SDT)이 새는 지점이다.

| 순간 | 연출 |
|---|---|
| 룬 시너지 **단계 상승** (1→2→3→4) | 화면 가장자리 속성색 파동 + 단계 배너 + 효과 요약 1줄 |
| **속성 반응 최초 발동** (융해·초전도 등, 재련소 기획 §4) | 대형 배너 "**융해**" + 정지 0.15s + 반응 설명 |
| **서약 조립 완성** (원인×효과 결합) | 조각 2개가 맞물리는 연출 + 태그 시너지 표시 |
| **무기 진화** (+5 도달) | 배경 암전 → 무기 발광 → 선택 세트피스 (재련소 §7-2에 대사·연출 이미 작성됨) |
| **정예 처치** | 슬로우모션 + 보상 상자 낙하 |

### ④ 잭팟 — 낮은 확률의 큰 사건

| 시스템 | 잭팟 | 설계 출처 |
|---|---|---|
| 재련소 | 2단계 상승 / 니어미스 연출 | 재련소 기획 §3.5 |
| 정제소 | Legendary 오버로드 / **재점화**(결과 재굴림) / 쌍생(복제) / 과열 / 불티 | 정제소 §8 — **발동률 ~18%, 전부 이득 방향** |
| 룬 굴림 | **9칸 3×3 (5%)** — 존 하나의 절반 | 재련소 기획 §2.3-② |
| **방 구조 (신규)** | **보물방 조우** — 진단서 §4-G "보물방 없음"의 해답 | 본 문서 §3-5 |

> **"재련 도파민 재기획"의 핵심 = 두 정거장의 감정을 분리한 것**:
> **재련소** — 손실 회피. *"한 번만 더 하면 +10인데…"* 멈추는 이유는 **무서워서**.
> **정제소** — 탐색·수집. *"이번엔 나오겠지."* 멈추는 이유는 **원석이 떨어져서**.
> 이 분리가 유지돼야 정거장 2개가 서로를 잡아먹지 않는다.

### ⑤ 랜덤의 방향 — "런마다 다른 목표"

정제소 기획 §2.3-①의 **숨은 속성 가중치**가 이 축의 핵심이다.

```
무속성:  랜덤한 건 "경로"뿐. 목표는 내가 정함  →  매 런 같은 빌드
유속성:  랜덤이 "목표"를 민다                  →  매 런 다른 빌드

런마다 숨은 가중치 (선언하지 않음): 🔥30% ⚡24% 🌑18% ❄13% ✦9% ☘6%
→ 아무도 안 알려줬는데 플레이어가 "이번 판은 불이 많이 나오네"를 스스로 느낀다
→ 그리고 4단계까지 딱 2칸 모자라게 설계 → 여기서 도박이 시작된다
```

**이것이 "랜덤 요소를 강하게"의 정답이다** — 결과를 랜덤하게 만드는 게 아니라, **매 런의 목표를 랜덤하게** 만드는 것.

## 2-3. 이어하기 동기 재정의

### 문제 재정의

`리뷰/meta-progression-design.md` §0-1:
> *"'한 판 더'의 핵심은 기억이 아니라 **재개 욕구**다. Zeigarnik 효과는 2025년 메타분석에서 부정됐고, 살아남은 건 **Ovsiankina 효과**(중단된 일을 재개하려는 욕구). 설계 함의: **다음 목표를 코앞에 노출 + 재시작 마찰 제거**."*

RelicFairy는 **재시작 마찰(세이브/이어하기)은 이미 해결됐다.** 남은 건 **"다음 목표 노출"** 하나다.

### 3개 층위의 목표 노출

```
[세션 단위]  런 목표      — "이번 런에서 뭘 하려는 거였지?"
[런 단위]    진행 상태    — "보스까지 몇 방 남았지?"
[메타 단위]  다음 해금    — "다음에 뭐가 열리지?"
```

#### ① 런 목표 (Run Goal) — 신규 개념

런 시작 시 **3개 중 1개를 고른다**(또는 자동 부여). 달성하면 **유물 코어 보너스**.

| 목표 예시 | 판정 | 코어 |
|---|---|---|
| **챕터 2 도달** | 기본 목표(항상 부여) | +3 |
| 정예 3회 처치 | 카운터 | +5 |
| 무기 +8 도달 | 재련소 | +5 |
| 한 속성 4단계 달성 | 룬 그리드 | +6 |
| 무피격 방 5개 클리어 | 챌린지 오버레이 재사용 | +8 |

- **죽어도 달성분은 정산된다** → "실패한 런"이 사라진다
- 목표는 **HUD에 항상 1줄** 떠 있다 → 런 도중에도 "지금 뭘 하는 중인지"가 명확
- 해금 트리와 연결: *"[대검] 해금까지 코어 12 — 이번 목표 3개 다 하면 14"*

#### ② 런 진행바 — `BuildPlan()`은 이미 답을 알고 있다

`RunSequencer.BuildPlan()`이 런 시작 시 **보스까지 전 깊이의 종류를 미리 산출**한다(진단서 §3-1). 이것을 **그대로 HUD에 그린다.**

```
Ch1  ●━━●━━◆━━◇━━○━━○━━○━━▣━━☠     현재 3/8 · 보스까지 5방
     ↑현재    ↑정예   ↑상점        ↑보스
```

- 지나온 방 = 채워짐 / 앞으로 = 종류 아이콘만(정확한 배치는 진단서 A 개선 여부에 따라 **확정 or 확률 표시**)
- **이것 하나로 §1-2-② "런에 목표가 없다"가 절반 해결된다** — 진행이 눈에 보이면 그만두기 어려워진다

#### ③ 결과 화면 = 다음 세션의 시작점

```
┌──────────────────────────────────────┐
│  영혼이 돌아왔다                       │   ← "GAME OVER" 아님
│  심연 도달 깊이 7 · 최고 기록 9        │
│                                       │
│  획득  유물 코어 +11                   │   ← 카운트업 연출
│        (미소비 원석 8 → 코어 +2 환산)   │
│                                       │
│  달성  ✅ 챕터2 도달   ✅ 정예 3회      │
│        ⬜ 무기 +8 (도달 +6)            │
│                                       │
│  ▸ 다음 해금:  [대검]  코어 12 / 24    │   ★ Ovsiankina
│    ████████░░░░░░░░  절반             │
│                                       │
│         [ 다시 잠행 ]  [ 베이스캠프 ]   │   ← 마찰 최소
└──────────────────────────────────────┘
```

> **"이어하기"의 의미가 바뀐다.** 지금은 "중단된 런을 복원한다"(기능)지만, 이 설계 후에는 **"진행 중인 성장 서사로 복귀한다"**(동기)가 된다.

# 3. 방 구조 개편안 — 6대 결함별 해법

> 진단서 §6 "우선 검토 축 8개"를 **결정된 설계**로 확정한다.

## 3-1. [결함 A] 선택이 미래를 바꾸게 — 문 위 보상 미리보기

### 결정: **"경로 의존 RNG"가 아니라 "보상 프리뷰"를 채택** (하데스 방식)

두 가지 길이 있었다:

| 안 | 내용 | 판정 |
|---|---|---|
| A-1. 경로 의존 시드 | `Combine(seed, visitCount)` → `Combine(seed, visitCount, 선택누적)` | ❌ **기각** — 플레이어가 인지할 수 없는 변화. `BuildPlan()` 사전 산출·드리프트 검증(`VerifyAgainstPlan`)이 전부 깨진다 |
| **A-2. 보상 프리뷰** | 문 위에 **무엇을 주는지** 표시. 종류가 아니라 **보상**을 고르게 | ✅ **채택** — 하데스가 실제로 하는 것. 인지 가능. 기존 HUD 재사용 |

**핵심 통찰:** 진단서 §5-1이 말하듯 *"플레이어가 느끼는 선택의 90%는 방 안에서 일어난다"*. 그러니 **방 안의 보상을 문 밖으로 끌어내면**, 경로 RNG를 안 건드리고도 "선택이 미래를 바꾼다"가 성립한다.

### 프리뷰에 담을 정보

```
현재:   ◆ 정예                    ← 방 종류만
개편:   ◆ 정예  🔥 Epic확정 +강화재료   ← 종류 + 보상 속성 + 등급 + 연료
        ○ 전투  ❄ 원석4
```

| 표시 항목 | 소스 | 왜 이게 선택을 만드는가 |
|---|---|---|
| 방 종류 (현행) | `DoorPlan.kind` | — |
| **보상 룬 속성** | 클리어 보상 3지선다를 **미리 롤**해서 대표 속성 1개 노출 | *"불 3단계까지 2칸 남았는데 저긴 얼음이네"* → **빌드가 경로를 결정** |
| **rarity floor** | §2-2-① 표 | *"정예는 Rare 확정이구나"* → 리스크↔리워드 |
| **연료 종류** | `FuelKind` | *"강화재료가 필요해 — 재련소 전에 정예를 타자"* |

> **구현 관점:** `DoorPlan`에 `rewardHint` 필드 1개 추가 → `RunFlowController.RevealGates`가 `ExitCompassHud.SetExits`에 넘기는 `label` 문자열을 확장. **HUD·게이트·시퀀서 구조 변경 없음.**

### 이것만으로 A가 해결되는가?

**부분적으로.** 다음 *깊이의 종류 쌍*은 여전히 시드 고정이다. 하지만 플레이어 체감상 **"내가 고른 문이 내 빌드를 바꿨다"** 가 성립하면 A의 증상(선택의 무의미함)은 사라진다. 완전한 노드맵 전환은 P3(§5)로 미룬다 — 비용 대비 효과가 낮다.

## 3-2. [결함 F] 정예 = 리스크↔리워드

## 3-3. [결함 E] 보스 전 빌드업 — 페이싱 재배열

### 현재 (Ch1)

```
#0 시작 · #1~3 자유 · #4 상점 · #5 이벤트 · #6 재련소 · #7 정제소 · #8 자유 · #9 통로 · #10 보스
```

### 개편 — **"투자 → 시험 → 투자 → 결전"**

### 부수: `shop_chance = 0.25`의 사문(死文) 수정

진단서 §3-2:
> *`CanRollRandomSpecial`의 예약 규칙(`used + RemainingMilestones < max`) 때문에 shop_cap=1인데 visit 4에 Shop 마일스톤이 있으므로 확률 롤이 절대 통과하지 못한다. **상점은 전 챕터에서 오직 visit 4에서만, 정확히 1회만 등장한다.***

**수정안: `shop_cap`을 1 → 2로 올린다.** 그러면 `0 + 1 < 2` = true가 되어 확률 롤이 살아난다.
- 마일스톤 1회는 **보장**(경제 허브 유지)
- 확률 1회는 **보너스**(런마다 다름 = 랜덤 요소)
- 골드 인플레 위험은 **상점 가격 스케일링**(v0.2 §7-4 "가격·드랍 동반 스케일링")으로 흡수

같은 논리로 `crucible_cap` / `refinery_cap`도 검토하되, **정제소는 §3-3에서 상시 UI로 옮기므로 방 캡은 1 유지**.

### 인카운터 다양성 — 토큰을 방에서 떼어낸다

진단서 §2-2:
> *"같은 티어 안의 방들은 스포너 토큰이 전부 같다. Ch1의 Normal 13개는 실질적으로 '15마리 인카운터' 6종 + '28마리 인카운터' 7종, 즉 **전투 자체는 2가지**다."*

**개편: `방 템플릿(공간)` 과 `인카운터(적 조합)` 를 분리한다.**

```
현재:  방 템플릿 = 지형 + 장식 + 스포너 토큰(고정)          → 방 13개 = 전투 2종
개편:  방 템플릿 = 지형 + 장식
       인카운터 테이블 = (챕터, 깊이, 카테고리) → 적 조합    → 방 13개 × 인카운터 8종 = 104조합
```

인카운터 축 예시(챕터당 6~8종):
| 인카운터 | 구성 | 요구하는 플레이 |
|---|---|---|
| 다수 약체 | 근접 소형 ×20 | 광역 |
| 소수 정예 | 중형 ×4 | 단일 딜 |
| 원거리 진지 | 원거리 ×6 + 방패 ×3 | 접근·돌파 |
| 혼성 웨이브 | 3웨이브 점증 | 지속력 |
| 소환사 | 소환사 ×2 + 무한 잡몹 | 우선순위 판단 |
| 돌진 러시 | 고속 근접 ×12 | 회피·포지셔닝 |

> **재사용:** `MonsterSpawner`의 `WaveEntry[]` / `WaveCount` / `LuckRollTableSO` 등급 필터가 이미 있다(v0.2 §6-5). 인카운터 테이블은 **CSV 1장 + 적용 지점 1곳**(`GameRunBootstrapper.ApplyMonsterSpawnerPlan`, 진단서 부록 A)이면 성립한다.

## 3-6. [결함 D] 난이도 곡선 실효화

### 세 가지를 동시에 고쳐야 한다

**① 커브 상한이 풀 분포에 못 미친다**

```
difficulty_curve 상한 = 전 챕터 1.8 고정
풀의 difficulty_scale 최대 = Ch2 2.1 / Ch3 2.8 / Ch4 3.64,  Elite는 Ch3 3.6 / Ch4 4.68
→ 타깃이 도달 못 하는 구간에 방들이 몰려 있다 → 전체 폴백(균등 추첨)
```

**수정:** 커브 상한을 **챕터별 풀 최대값에 정렬**.

| 챕터 | 현재 | 개편 |
|---|---|---|
| Ch1 | `0:0.4\|8:1.8` | `0:0.4\|9:2.0` |
| Ch2 | `0:0.5\|10:1.8` | `0:0.6\|10:2.2` |
| Ch3 | `0:0.6\|10:1.8` | `0:0.8\|10:2.9` |
| Ch4 | `0:0.7\|12:1.8` | `0:1.0\|12:3.7` |

**② Elite는 별도 커브가 필요하다** — 진단서 §4-D-2: **Ch2~4 Elite는 전 구간 0/4 미스**, 즉 4챕터 전부 균등 추첨. Elite 풀의 `difficulty_scale`(Ch3 3.6 / Ch4 4.68)에 맞춘 **`elite_difficulty_curve` 별도 컬럼**을 신설하거나, 최소한 `DifficultyTolerance 0.35`를 **상대값(target × 0.25)** 으로 바꾼다.

**③ 챕터 내부에 몹 스탯 램프가 아예 없다**

```csharp
// MonsterBase.cs:402
_difficultyScale = run.CurrentDifficultyScale;
// GameRunSession.cs:94
return chapterScale * (1f + AbyssDepth * LoopScalePerDepth);   // ← chapterScale은 챕터당 상수
```

**수정:** `CurrentDifficultyScale`에 **깊이 램프**를 곱한다.

```
CurrentDifficultyScale = chapterScale
                       × (1 + AbyssDepth × LoopScalePerDepth)
                       × (1 + visitCount / bossThreshold × depthRamp)   ← ★신규
```

`depthRamp = 0.25` 시작점 → 챕터 첫 방 대비 보스 직전이 **+25% 강함**. 이 한 줄이 "챕터 안에서 점점 어려워진다"는 체감 전체를 담당한다.

> ⚠️ **밸런스 회귀 위험 최상.** 이 항목만은 반드시 **디버그 노브로 on/off 가능**하게 하고(기존 `bossThresholdOverride` 패턴 재사용), 실측 후 값을 정한다.


- 재화 pill: **획득 시에만 밝아졌다가 감쇠** → 평소엔 시야를 안 뺏는다
- 시너지: 단계만 압축 표시, 상세는 Tab

### ② 문 선택 (클리어 직후)

```
        ┌──────────────┐          ┌──────────────┐
        │  ◆ 정예       │          │  🏪 상점      │
        │  🔥 Rare확정   │          │  ⚠ 이 챕터    │
        │  🔨강화재료+2  │          │    마지막      │
```

- **`⚠ 이 챕터 마지막` 배지가 이 설계 전체에서 가장 저렴하고 효과 큰 한 줄이다** (결함 C 대응)
- 기존 `ExitCompassHud`의 `(target, label, color)` 구조를 **다중 라인 라벨**로 확장하면 끝

### ③ 보상 3지선다

- 카드 크기 = **희귀도에 비례**(Legendary가 물리적으로 더 크다)
- **"내 빌드에 어떻게 작용하는지"를 카드에 표기**: *"🔥 불 3단계 → 4단계 (2칸 부족)"*
- 정예/보물방은 **카드 등장 연출 자체가 다르다**(§2-2-②)

# 7. 결론 — "이것부터 하면 된다"

## 한 문장

> **P0 9개 항목 중 6개가 "이미 있는 코드에 인자 하나 넘기기 / CSV 값 바꾸기 / 화면에 표시하기"다.**
> RelicFairy는 시스템이 부족한 게 아니라, **만들어 놓은 시스템이 플레이어에게 안 보이고 서로 안 걸려 있다.**

## 세 루프의 현재 상태와 목표

| 루프 | 현재 | P0 후 | P1 후 |
|---|---|---|---|
| **런 사이(메타)** | ❌ 스탯 6종만 | △ 죽음이 진전으로 프레이밍됨 | ✅ **해금 = 다음 런이 달라짐** |
| **런 내(도파민)** | △ 방 안에만 | ✅ 문 선택·정예·희귀도가 도파민이 됨 | ✅ 빌드 폭발 연출 + 방 서프라이즈 |
| **세션 사이(복귀)** | ❌ 기능만 있고 동기 없음 | ✅ **진행바 + 목표 + 다음 해금 노출** | ✅ 해금 트리가 장기 목표를 공급 |

## 착수 순서 권고

```

        P0-7/8 재화 pill + 색 통일
4주차:  P0-9 휴식방
──────────────────────────────────  ▶ 여기까지가 데모
이후:   P1-1 해금 트리 (세이브 마이그레이션 포함, 가장 큰 덩어리)
```
