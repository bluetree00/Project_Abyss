## 1-2. 그 위에 얹히는 "원동력" 공백 (통합설계서 §1-2)

| 공백 | 실측 |
|---|---|
| **죽음에 의미가 없다** | 영구 성장 = `UserGameData`의 스탯 6종 각성뿐. **해금 목록 필드 0건.** 100판을 해도 늘어나는 건 숫자뿐 |

## 1-3. 이번 세션에서 이미 해소된 것 (중복 설계 방지)

# 2. 소모성 방구조 상세 설계

## 2-0. 한 문장 정의

> **특수방은 챕터당 한정 자원(토큰)이다. 방 구조는 시드가 아니라 "남은 토큰 상태"에서 매번 다시 생성된다.**
> 미소모 타입은 문 후보에 등장하고, 소모된 타입은 후보에서 빠지며 그 자리를 다른 타입이 메운다.
> 그래서 **"내가 상점을 썼다"가 이후 방 구조를 실제로 바꾼다.**

## 2-1. 토큰 모델 — 신규 개념이 아니라 기존 카운터의 의미 전환

현재 이미 4개의 카운터가 있다.

```csharp
// RunSequencer.cs:74-77  — 현재
private int _shopUsed;
private int _eventUsed;
private int _crucibleUsed;   // 챕터당 1 (마일스톤 강제 전용)
private int _refineryUsed;   // 챕터당 1 (마일스톤 강제 전용)
```

이 카운터의 **의미만 바꾼다.**

| | 현재 의미 | 개편 의미 |
|---|---|---|
| 증가 시점 | **문을 굴릴 때**(`RollExits` 안, `:176`) | **플레이어가 실제로 이용했을 때** |
| 무엇을 세는가 | 시퀀서가 배치한 횟수 | 플레이어가 소비한 횟수 |
| 플레이어 가시성 | 없음 | **HUD에 잔량 상시 표시** |

**토큰 초기값 (챕터당) — 시작점:**

| 토큰 | 개수 | 근거 |
|---|---|---|
| 🏪 상점 | **1** | 현행 CSV `shop_cap=1`과 동일. 경제 허브 1회 보장 |
| ◇ 이벤트 | **1** | 현행 `event_cap=2`에서 축소. 2개면 희소성이 안 생긴다(§2-5) |
| 🔨 재련소 | **1** | 현행 하드코딩 `< 1` 유지 |
| 💎 정제소 | **1** | 현행 하드코딩 `< 1` 유지 |

> **총 4토큰 / 챕터.** Ch1 기준 11방 중 4방이 특수방 후보 — 현행 스파인(4:Shop 5:Event 6:Crucible 7:Refinery)과 총량이 같다. **밸런스 총량을 건드리지 않고 배치 방식만 바꾸는 것**이 이 설계의 안전 장치다.

## 2-2. 소모 시점 — "입장"이 아니라 "이용"

**확정 방향: 실제 이용 시 소모. 입장만으로는 토큰이 유지된다.**

| 방 | 소모 트리거 | 코드상 후크 |
|---|---|---|
| 상점 | **최초 구매 성공 1건** | `ShopRoomController.BuyProduct()` 성공 반환(`ShopPurchaseResult.Success`) 지점 |
| 이벤트 | **챌린지 수락/개시** | `IInteractionChallenge` 개시 또는 `CombatChallengeOverlay` 활성화 |
| 재련소 | **강화·도박 시도 1회** | 재련 롤 지점(`RunMetaSnapshot.crucibleRollIndex`가 이미 롤 수를 세고 있음) |
| 정제소 | **정제 1회** | 룬 정제 확정 지점 |

**왜 "입장 소모"가 아닌가 — 이것이 이 설계의 심장이다.**

```
입장 소모:  문을 고르는 순간 결정 끝. 방 안은 소화 과정.
이용 소모:  들어가서 "재고를 보고" → 살지 말지 결정 → 안 사면 토큰이 남는다
            → 남은 토큰은 다음 문 후보를 바꾼다
            → "엿보고 물러나는" 전략이 성립한다
```

**"엿보기"가 공짜면 안 된다.** 입장 자체에 비용을 붙인다(택1, §6 열린 결정):

| 안 | 내용 | 평가 |
|---|---|---|
| **(가) 깊이 비용** | 특수방 입장도 `visitCount++` → 보스까지 남은 방을 1 소비 | ✅ **추천** — 이미 `CommitEntry`가 하는 일. 코드 0줄. "엿보면 전투 기회 1번이 사라진다" |
| (나) 재입장 금지 | 한 번 본 특수방은 그 챕터에 다시 안 나옴(소모 여부 무관) | ❌ 토큰 개념과 충돌(안 썼는데 사라짐 = 결함 C 재발) |
| (다) 엿보기 요금 | 입장 시 골드/HP 소량 차감 | △ 명시적이지만 짜증 유발. 보류 |

> (가)를 쓰면 **"보스까지 남은 방 수"가 진짜 자원이 된다.** 진단서 §3-3의 "Ch1 = 11방" 총량이 그대로 예산이 되고, 상점 구경 한 번이 전투방 하나를 먹는다. 런 진행바(§4-2)가 이 비용을 눈에 보이게 만든다.

## 2-3. 구조 생성 — 시드에서 소모 상태로

### 현재

```csharp
// RunSequencer.RollExits()
var rng = new System.Random(Combine(_seed, _visitCount));   // :168  ← (시드, 깊이)만
RoomPlanKind? forced = _config?.GetMilestoneKind(_visitCount + 1);
if (forced.HasValue) NoteForcedSpecial(forced.Value);       // :176  ← 롤 시점 소진
```

### 개편

```
① RNG 시드에 소모 상태를 넣는다
   Combine(seed, visitCount)  →  Combine(seed, visitCount, TokenStateHash)
   TokenStateHash = 남은 토큰 4종의 비트/정수 조합 (예: shop*1 + event*2 + crucible*4 + refinery*8)

② 문 후보 집합을 잔여 토큰에서 만든다
   후보 = { 소모되지 않은 특수 타입 } ∪ { Normal, Elite }
   소모된 타입은 후보에서 제외 → 그 슬롯을 Normal/Elite가 승격해 채운다

③ NoteForcedSpecial 제거
   토큰은 "이용"이 소비한다(§2-2). 롤도 커밋도 토큰을 건드리지 않는다.

④ 마일스톤은 "강제 배치"에서 "우선 배치"로 격하
   GetMilestoneKind가 반환한 종류가 아직 미소모면 문0에 우선 배치.
   이미 소모됐으면 무시하고 다음 미소모 타입으로 대체.
```

**이것이 왜 결함 A를 실제로 해결하는가:**

`TokenStateHash`는 **플레이어의 소비 이력**이다. 문 선택 → 방 이용 → 토큰 변화 → 다음 롤의 시드 변화 → **다음 방 종류가 실제로 달라진다.**

> 📌 **통합설계서 §3-1의 "A-1 경로 의존 시드 기각" 판정을 이 문서가 뒤집는다 — 전제가 달라졌기 때문이다.**
> 당시 기각 사유는 두 가지였다: ① *"플레이어가 인지할 수 없는 변화"* ② *"`BuildPlan()` 사전 산출·`VerifyAgainstPlan` 드리프트 검증이 전부 깨진다"*.
> ①은 **소모 상태에서는 성립하지 않는다** — 플레이어는 자기가 상점을 썼다는 걸 안다. 인지 가능한 상태 변수다.
> ②는 **여전히 유효한 비용**이다. 대처는 §2-8에 명시한다.

### 소모된 자리를 무엇이 채우는가 (필수 결정)

토큰 하나가 빠지면 문 후보 슬롯이 하나 빈다. 그 자리를 무엇으로 채울지가 **소모의 체감을 결정한다.**

| 채움 규칙 | 체감 | 평가 |
|---|---|---|
| **Normal/Elite 승격** | *"상점을 다 썼으니 이제 싸울 일만 남았다"* — 후반이 전투로 수렴 | ✅ **기본 채택**. 진단서 E(보스 전 비전투 4연속)를 자동으로 고친다 |
| 다른 특수 타입으로 치환 | *"상점을 썼더니 재련소가 열렸다"* | △ = 대안 C(§2-4). 토큰 총량을 늘리지 않고도 다양성이 생기지만, "소모"의 무게가 가벼워짐 |
| 빈 슬롯 그대로(문 1개) | 외길 증가 | ❌ 결함 B 악화 |

> **기본 = Normal/Elite 승격.** 결과적으로 **런의 전반부는 특수방이 밀집하고 후반부는 전투가 밀집**한다. 이는 "투자 → 시험 → 결전"이라는 통합설계서 §3-3의 페이싱 목표와 자연히 일치하고, **CSV 마일스톤을 손대지 않고도** 달성된다.

## 2-4. 재등장 규칙 — 확정안과 대안 비교

**확정: (A) 챕터당 1회 소진 — 희소성 우선.**

| 안 | 규칙 | 긴장 성립 | 밸런스 리스크 | 구현 비용 | 판정 |
|---|---|---|---|---|---|
| **(A) 챕터당 소진** | 이용하면 그 챕터엔 끝. 다음 챕터에 토큰 리필 | ✅ **최상** — "지금 쓸까 아껴둘까"가 직접 성립 | 중 — 상점 0회 런이 나올 수 있음(§2-5가 완화) | **소** — 기존 카운터 재사용 | ✅ **채택** |
| (B) 쿨다운 재생성 | 이용 후 N방 뒤 재등장(토큰 리필) | △ — 기다리면 다시 오므로 아끼는 이유가 약함 | 하 | 소 — `_cooldowns` 배관 존재(`RunSequencer.cs:350-366`) | 대안 |
| (C) 소모 시 타 타입 개방 | 상점 소모 → 재련소 등장 확률↑ | △ — 소모가 "손실"이 아니라 "전환"이라 무게가 가벼움 | 중 | 중 | 대안 |
| (D) 자동 소모 = **현행** | 롤 시점에 소진(`NoteForcedSpecial`) | ❌ — 플레이어가 관여하지 않는 소모 | — | — | ❌ **폐기** |

**(A)에 붙는 필수 부속 규칙 3가지:**

1. **챕터 경계에서 리필.** 토큰은 챕터 스코프다. Ch1에서 다 써도 Ch2에서 4개 새로 받는다. → *"이 챕터에서 다 쓰자"*가 합리적 전략이 되고, 아끼는 행위가 **챕터 내부의 타이밍 게임**으로 국한된다(챕터를 넘는 저축 불가).
2. **미사용 토큰 소액 환급.** 챕터 클리어 시 남은 토큰당 유물 코어 +1. → "안 쓴 게 완전한 손해"는 아니되, **쓰는 편이 항상 낫게** 환급액을 낮게 둔다. 무한 보류를 막는 안전장치이자, 어쩔 수 없이 못 만난 경우의 보상.
3. **소모 즉시 UI 반영.** 토큰이 0이 되는 순간 문 프리뷰에서 해당 아이콘이 회색으로 죽고, HUD pill이 소진 연출을 낸다(§4).

## 2-5. "아껴둘 이유"의 설계 — 긴장이 실제로 성립하려면

> **경고:** 토큰만 만들면 플레이어는 **무조건 처음 만난 상점에서 쓴다.** 나중이 더 좋다는 보장이 없으면 "아낀다"는 선택지는 존재하지 않고, 소모성 구조는 **그냥 "특수방을 한 번씩 만나는 현행"과 같아진다.**

**아껴둘 이유 4종 (전부 넣지 말고 ①②는 필수, ③④는 선택):**

| # | 장치 | 내용 | 재사용 배관 |
|---|---|---|---|
| **①** | **후반 재고가 더 좋다** (필수) | 상점 진열 등급 하한이 `visitCount`에 비례. 초반 상점 = Common/Rare 중심, 후반 상점 = **Rare 하한 + Epic 빈도↑** | `RoomRewardTable.RarityWeights` 구조를 상점 진열에 그대로 이식. `AbyssPeddlerCatalog`의 `RarityPrice(rarity)` 존재 |
| **②** | **챕터 길이 = 하드 리밋** (필수) | `boss_threshold`(Ch1=8) 도달 시 보스 어프로치 확정(`RunSequencer.cs:159-165`). **무한 보류 물리적 불가** — 안 쓰면 챕터와 함께 사라진다 | 현행 그대로. 코드 0줄 |
| ③ | **자원이 나중에 모인다** | 지금은 골드 200, 좋은 물건은 500. "지금 사면 잡템, 나중이면 본품" | `PlayerRunState.TempGold` |
| ④ | **빌드가 나중에 확정된다** | 룬 시너지가 3~4방 뒤에야 방향이 잡힘. 재련소를 일찍 쓰면 "안 쓸 무기"를 강화하게 됨 | 룬 그리드 · `RunFuelBank` |

**①과 ②가 함께 있어야 긴장이 성립한다:**

```
①만 있으면 →  무조건 마지막까지 아낀다 (후반이 항상 우월)
②만 있으면 →  무조건 처음에 쓴다 (사라질까 봐)
①+②      →  "몇 번째 상점에서 쓸까"가 진짜 판단이 된다
              후반이 좋지만, 후반 상점을 못 만날 위험도 있다
```

> ⚠️ **위험 인지:** ①을 넣으면 "초반 상점은 함정"이 될 수 있다. 완화 = **초반 상점에만 붙는 고유 가치**(가격 할인 20% 또는 즉시 효과 소모품 특화). 진열 등급은 낮지만 **가격 효율은 초반이 낫게** 설계한다. → §6 열린 결정 #3.

| 연료 종류·양 | `Rule.Ore` / `Rule.EnhanceMaterial` | *"강화재료가 필요해 — 재련소 전에 정예를 타자"* |

### 구현 관점 — 신규 배관 0

`ExitCompassHud.SetExits`가 받는 `label`은 **자유 문자열**이다(`ExitCompassHud.cs:74·88`).

```csharp
// RunFlowController.cs:783-785  현재
marks.Add((tr, KindGlyph(exits[i].kind) + " " + KindKor(exits[i].kind), KindBrightColor(exits[i].kind)));
```

→ 이 문자열을 **여러 줄로 만들면 끝**이다. 단, `ExitCompassHud.cs:96` `textWrappingMode = NoWrap` + `rt.sizeDelta = (300, 60)`이므로 **줄바꿈(`\n`) 허용 + 높이 확대**가 함께 필요하다. 게이트 월드 라벨(`RunFlowController.cs:1125`)도 같은 문자열 생성 경로라 **한 곳을 고치면 둘 다 반영**된다.

> **정보량 상한 경고:** 3줄을 넘기면 전투 직후 화면에서 읽히지 않는다. **2줄 고정**(1행: 종류+글리프 / 2행: 토큰 또는 보상 요약)을 권고하고, 상세는 게이트 근접 시에만 3행으로 확장한다.

## 2-7. 외길 복도 개선 — 소모성 구조에서는 더 치명적이다

진단서 §2-1: Shop/Crucible/Refinery/PreBoss/비전투Event의 `grid_csv` 출구 DR이 **1개**. Ch1 11방 중 갈림길은 4~5개이고 **전부 전반부**.

**소모성 구조에서 이게 왜 더 나빠지는가:** 토큰을 쓴 직후는 **구조가 방금 바뀐 순간**이다. 그 결과(새 문 후보)를 즉시 보여줘야 "내 선택이 구조를 바꿨다"가 성립하는데, **특수방 출구가 1개면 바로 그 순간에 선택지가 없다.**

| 방 | 현재 출구 | 개편 | 비고 |
|---|---|---|---|
| Shop / Crucible / Refinery | 1 | **2** (East DR 추가) | ⚠️ 격자 제약 확인 필요 — `MAP_TOKENS.md` + 1m 셀/벽 12층 규약 |
| 비전투 Event (sanctum/gamble/vault/oracle/sacrifice) | 1 | **2** | 동일 |
| PreBoss | 1 | **1 유지** | 보스 직전은 외길이 맞다(긴장 집중) |

> **저비용 대안 (East DR이 격자상 불가할 때):** 특수방 **안**에서 다음 문 2개를 미리 보여준다 — 상점 벽면/재련소 모루 옆에 "다음: ○ 전투 / ◆ 정예" 예보 패널. 선택지는 못 늘려도 **"쓰고 나가면 무엇이 기다리는지"**를 알려주므로, 토큰 소비 판단에 필요한 정보는 회복된다.
> ⚠️ **커스텀 프리팹 방(`Road_Boss_ChN` 등)은 씬 인스턴스라 지오메트리 이동 금지** 규칙이 걸린다. East DR 추가 대상에서 제외한다.

### Elite와의 연계 — 리스크로 주도권을 되사는 축

`RoomRewardTable`에 이미 Elite = `floor Rare + 후보4 + ore6 + enhance2`가 들어있다. 소모성 구조와 연결하는 두 가지 안:

| 안 | 내용 | 평가 |
|---|---|---|
| **(가) 연료 → 토큰 활용도** | Elite가 주는 `enhanceMaterial 2`가 **재련소 토큰의 값어치를 올린다**. 정예를 탄 사람만 재련소를 제대로 쓴다 | ✅ **추천** — 코드 0줄. 이미 그렇게 되어 있다. 문 프리뷰에 연료를 표기하기만 하면 성립 |
| (나) Elite 클리어 = 토큰 1 재충전 | 위험을 감수하면 소모한 토큰이 돌아옴 | △ — 강력하지만 §2-5의 희소성을 정면으로 깎는다. **P2 이후 재평가** |

## 2-8. 치러야 할 비용 — `BuildPlan` / `VerifyAgainstPlan` / 이어하기

소모 상태를 시드에 넣으면 **런 시작 시점에 전 깊이를 미리 아는 것이 원리적으로 불가능**해진다. 정직하게 적는다.

| 대상 | 현재 | 개편 후 | 대처 |
|---|---|---|---|
| `BuildPlan()` (`RunSequencer.cs:129-142`) | 런 시작 시 보스까지 전 깊이 종류를 **확정** 산출 | 소모 이력에 의존하므로 **확정 불가** | **"일정표"에서 "예보"로 격하.** 현재 토큰 상태를 그대로 유지한다고 가정한 **낙관 예보** 1개만 산출 → 진행바(§4-2)의 밑그림으로 사용. 토큰이 변하면 재계산 |
| `VerifyAgainstPlan()` (`:707`) | 라이브 롤과 일정표 불일치 시 경고 | **상시 불일치** → 경고 스팸 | **드리프트 검증 폐기** 또는 "토큰 변화로 인한 차이"를 정상으로 인정하는 재계산형으로 교체 |
| `DumpRunPlan()` (`:689`) | 콘솔 덤프 = 레벨디자인 검증 도구 | 확정성 상실 | 유지하되 **"예보"라고 표기**. 레벨디자인 검증은 "토큰 시나리오별 덤프"(전부 쓴 경우 / 전혀 안 쓴 경우)로 대체 |
| **이어하기** (`RunMetaSnapshot`) | `shopUsed`·`eventUsed`만 저장. **`_crucibleUsed`·`_refineryUsed` 미저장** ⚠️ | 토큰 4종 전부가 **핵심 진행 상태** | `RunMetaSnapshot`에 `crucibleUsed`·`refineryUsed` **필드 추가 필수** + `RunSequencer.RestoreState` 시그니처 확장. **기존 구멍을 함께 막는 작업** |
| 세이브 재현성 | *"롤 전 상태로 저장해두면 복원 때 같은 시드로 다시 굴려 동일한 출구가 재현된다"*(`RunFlowController.cs:672-674`) | 토큰이 복원되면 동일 재현 **유지됨** | 위 필드 추가로 성립. **저장은 여전히 `RollExits()` 앞에서** |

> **이 비용은 지불할 가치가 있다.** `BuildPlan`의 확정성은 **디버그 편의**이고, 잃는 대가로 얻는 것은 **플레이어 주도권**이다. 다만 진행바 UI(§4-2)를 "확정 일정표"로 그리면 안 된다 — **"예보 + 확정 구간"** 으로 그려야 한다.

# 3. 원동력 보강 설계

> 소모성 구조는 **런 안의 원동력**(주도권)을 만든다. 하지만 **런 사이의 원동력**(죽음의 의미)은 별개 축이다. 둘 다 없으면 "한 판 더"가 안 나온다.

## 3-1. 현황 — 해금이 0건이다

```
UserGameData.cs 전량:
  재화       level / experience / gold / jewel / heart
  통계       totalRuns / totalClears / highestChapter / totalGoldEarned / lichEncounterCount
  메타 해금  sealBrokenBossIds  ← 유일한 "해금". 보스 페이즈2 한정
  메타 성장  abyssEssence + awakeningLevel{Sword,Shield,Heart,Step,Mana,Luck}  ← 전부 수치
```

**무기·유물·룬·서약·시작보너스 해금 필드가 하나도 없다.** 100판을 해도 늘어나는 것은 6개 숫자뿐이고, **다음 런이 달라지는 경로가 데이터상 존재하지 않는다.**

## 3-2. 원칙 — 파워가 아니라 선택지

> 통합설계서 §2-1(meta-progression-design 인용):
> *"해금 = 난이도 하락이 아니라 **선택지 확장**(adds options, not power). 영구 파워 인플레는 런 내 선택의 무게를 죽인다."*

**소모성 방구조와 정면으로 맞물리는 지점이 여기다.** 소모성 구조는 "토큰을 어디에 쓸까"라는 **선택**을 만든다. 메타가 파워형이면 그 선택이 무의미해진다(강해서 아무 데나 써도 됨). **메타가 선택지 확장형이어야 소모성 구조가 산다.**

## 3-3. 해금 트리 — 5갈래 (통합설계서 §2-1 계승)

| 갈래 | 해금 대상 | 베이스캠프 거점 | 소모성 구조와의 연결 |
|---|---|---|---|
| **① 무기** | 무기 타입 + 진화 분기 | `WeaponForgeAltar` | **재련소 토큰의 가치를 정한다** — 강화할 무기가 여러 개여야 "이 무기에 쓸까" 판단이 생김 |
| **② 유물** | 유물 + 코어 파츠 풀 | `RelicAltar` | 유물마다 원하는 토큰이 다름(화상형=재련, 룬형=정제) |
| **③ 서약** | 원인/효과 조각 팔레트 | `CovenantPickup`/조립대 | 이벤트 토큰의 결과 다양성 |
| **④ 룬** | 속성 존·특수 룬 종류 | 정제소(런 내) + 도감 | **정제소 토큰의 가치** — 굴림 풀이 넓어야 정제가 기대된다 |
| **⑤ 시작 보너스** | 런 시작 조건 | `WorldAwakeningAltar` 확장 | **★ 시작 토큰 조정** — 예: *"상점 토큰 +1로 시작, 대신 정제소 토큰 0"* |

> **⑤가 소모성 구조와 가장 강하게 결합한다.** "공격력 +5%" 같은 파워형 대신 **"토큰 구성을 바꾸는" 스타일 해금**으로 설계하면, 파워 인플레 없이 **런 형태 자체가 달라진다.**
> 예시: `상인의 인장` = 상점 토큰 2 / 재련 토큰 0 · `대장장이의 인장` = 재련 토큰 2 / 상점 토큰 0 · `균형` = 현행 1/1/1/1.

## 3-4. 재화 — 신규 0

`abyssEssence`(유물 코어)의 **소비처를 넓히기만 한다.**

```
현재:  abyssEssence → 각성 6종 (TryUpgradeAwakening, UserGameData.cs:100)
개편:  abyssEssence → 각성 6종 + 해금 트리 5갈래 + (§2-4 부속②) 미사용 토큰 환급 유입
```

**각성 6종은 동결한다**(추가 확장 없음). 인플레를 막고, 신규 유입분은 전부 해금으로 흐르게 한다.

## 3-5. 세이브 스키마 — 리스크 최상 항목 ⚠️

**`UserGameData`에 해금 목록 필드를 신설해야 한다. 이것이 이 문서 전체에서 가장 위험한 작업이다.**

### 이미 있는 선례를 따른다

```csharp
// UserGameData.cs:22-24
/// <summary>봉인이 해제된 보스 id 목록(쉼표 구분 문자열). ...
/// 백엔드가 flat 컬럼(int/문자열)만 저장하므로 리스트 대신 CSV 문자열로 보관한다.</summary>
public string sealBrokenBossIds = "";
```

→ **동일 패턴으로 `unlockedIds`(쉼표 구분 문자열) 1개 필드.** `IsBossSealBroken`/`BreakBossSeal`(`:27-42`)를 그대로 본뜬 `IsUnlocked(id)`/`Unlock(id)` 2개 메서드.

| 설계 | 장점 | 단점 |
|---|---|---|
| **CSV 문자열 1필드** (권장) | 백엔드 flat 컬럼 제약 충족. **선례 존재** = 검증된 경로. 항목 추가 시 스키마 변경 0 | 문자열 파싱, 항목 수 늘면 길어짐 |
| 갈래별 필드 5개 | 타입 안전 | 백엔드 컬럼 5개 추가 = 스키마 변경 5회 |
| 중첩 객체/리스트 | 확장성 | ❌ **백엔드가 못 받는다**(주석 명시) |

### 회귀 위험과 완화

| 위험 | 완화 |
|---|---|
| 구세이브에 필드가 없어 로드 실패 | `= ""` 기본값 초기화(`sealBrokenBossIds`와 동일). `Reset()`(`:53-75`)에도 추가 |
| 백엔드 스키마 미반영 → 저장 유실 | `BackendGameData.ApplyRunResultAsync` 경로 동시 수정. **필드 추가 후 저장→재로드 왕복 테스트 필수** |
| 해금 이전 세이브의 사용자가 "이미 열려야 할 것"을 못 가짐 | **초기 해금 세트 정의**(무형검·가웨인 등 현행 사용 가능분을 기본 해금으로 부여) — 구세이브가 빈 문자열이어도 게임이 성립해야 한다 |
| 런 세이브(`RunMetaSnapshot`)와 혼동 | **별개다.** 해금 = 계정 영구(`UserGameData`), 토큰 = 런 스코프(`RunMetaSnapshot`). §2-8의 토큰 필드 추가와 **동시에 하지 말 것** — 실패 시 원인 분리가 안 된다 |

## 3-6. 런 목표 — 소모성 구조를 목표로 삼는다

런 시작 시 목표 3개를 **동시 부여**하고, 죽어도 달성분을 정산한다(통합설계서 §2-3 권고 계승).

**소모성 구조가 목표를 새로 공급한다:**

| 목표 | 판정 | 코어 | 소모성과의 관계 |
|---|---|---|---|
| 챕터 2 도달 | 기본(항상) | +3 | — |
| **토큰 4개 전부 소진하고 챕터 클리어** | 토큰 카운터 | +5 | **적극 활용 유도** |
| **토큰 2개 이상 남기고 챕터 클리어** | 토큰 카운터 | +5 | **절약 플레이 유도** (위와 배타 — 런마다 하나만 부여) |
| 정예 3회 처치 | 카운터 | +5 | `RoomRewardTable` 연료 축적 |
| 무기 +8 도달 | 재련소 | +5 | 재련 토큰 집중 |
| 한 속성 4단계 | 룬 그리드 | +6 | 정제 토큰 집중 |

> **"전부 쓰기" 목표와 "아끼기" 목표가 런마다 번갈아 나오면, 같은 시스템이 매 런 다른 플레이를 요구한다.** 소모성 구조 하나로 목표 축이 2개 생기는 셈이다.

## 3-7. 두 원동력의 연결

```
런 안의 원동력  =  주도권
   "토큰을 어디에 쓸까" → 내 선택이 방 구조를 바꾼다 → 이 런은 내가 만든 런이다

런 사이의 원동력  =  해금
   "죽었지만 코어 11 → 대검 해금까지 절반" → 다음 런은 다른 런이다

두 축의 결합점 = ⑤ 시작 보너스 해금 (§3-3)
   해금이 토큰 구성을 바꾼다 → 다음 런의 "주도권 형태"가 달라진다
   → 메타 해금이 런 내 선택을 죽이지 않고 오히려 다양화한다 (파워형 회피의 구조적 보장)
```

## 3-8. 죽음의 재프레이밍 (통합설계서 §2-3-③ 계승)

- `"GAME OVER"` 문구 금지 → **"영혼이 돌아왔다 — 심연 도달 깊이 7"**
- 결과 화면에 **다음 해금까지 남은 코어** 고정 노출 (Ovsiankina — 재개 욕구)
- **미사용 토큰 환급**(§2-4 부속②)을 결과 화면에서 카운트업 — *"쓰지 못한 상점 토큰 1 → 코어 +1"*. 실패한 런에도 정산할 것이 생긴다

# 4. UI 가독성 — 정보 위계

> 기존 HUD에는 이미 **버프창 5소스 단일 그리드**와 **효과 텍스트 표시 레이어**가 얹혀 있다. 그 위에 토큰·프리뷰·해금을 더 얹으면 **화면이 무너진다.** 위계부터 정한다.

## 4-1. 3층 위계

| 층 | 정의 | 위치 | 본 기획서가 추가하는 것 |
|---|---|---|---|
| **항상 보임** | 매초 판단에 쓰는 것 | HUD 고정 | **잔여 토큰 pill 4종** · 런 진행바 · 런 목표 1줄 |
| **맥락 보임** | 그 순간에만 필요 | 이벤트 발생 시 | **문 프리뷰 2줄** · 보상 카드 · 토큰 소모 순간 연출 |
| **온디맨드** | 깊이 파고들 때 | Tab / 팝업 | 빌드 요약 · **해금 트리 진행** |

## 4-2. 화면 배치안

```
┌──────────────────────────────────────────────────────────────┐
│ 💰1,240 🔨8 💎12 ◆34   │  🏪1 ◇1 🔨0 💎1  │  Ch1 ●●●◆○○○▣☠ 3/9 │ ← 항상
│  런 재화 4종            │   잔여 토큰 4종   │   진행바(예보)      │
│                                                               │
│ 🎯 토큰 4개 전부 쓰고 챕터 클리어 (2/4)                        │ ← 항상, 1줄
│                                                               │
│                        [ 게임 화면 ]                           │
│                                                               │
│ 🔥3 ⚡2                                    [버프 아이콘 그룹]   │ ← 항상(압축)
│ HP ████████░░   Q▮ E▮ R░                                      │
└──────────────────────────────────────────────────────────────┘
```

**토큰 pill 규칙:**
- 잔량 1 이상 = 컬러 / **0 = 회색 + 취소선**
- 소모 순간 = **pill이 한 번 밝아졌다가 회색으로 죽는 연출** (플레이어가 "썼다"를 반드시 인지해야 함)
- **마지막 1개 남은 토큰은 은은한 테두리 펄스** — 문 프리뷰의 `⚠ 이 챕터 마지막` 배지와 시각 언어를 일치시킨다

**진행바 규칙 (§2-8 반영):**
- 지나온 방 = 채워짐(확정)
- **앞으로의 방 = 예보** — 확정 아이콘이 아니라 **반투명 + 물음표 톤**으로 그린다. "토큰을 쓰면 바뀔 수 있다"를 시각적으로 알린다
- 보스방과 `boss_threshold` 도달선만 **확정 표기**(코드상 실제로 확정이므로)

## 4-3. 색 언어 — 축이 3개면 충돌한다

| 축 | 표현 수단 | 근거 |
|---|---|---|
| **희귀도** (Common회/Rare청/Epic자/Legendary금) | **프레임(테두리)** | `RoomRewardTable`의 `ItemRarity`가 정본 |
| **속성** (🔥⚡❄☘✦🌑) | **아이콘/배경** | 6속성 VFX 레지스트리와 일치 |
| **방 종류** | **텍스트 색** | `RunFlowController.KindBrightColor`(`:1138-1148`) **이미 존재 — 확장만** |
| **토큰 상태** | **채도**(활성=컬러 / 소진=회색) | 신규. 위 3축과 겹치지 않는 유일한 자유 축 |

> ⚠️ **희귀도 Rare 청 vs 얼음 속성 청**이 충돌한다(통합설계서 §4-2 기지적). 해결은 **위치 분리**: 희귀도=테두리, 속성=아이콘. 토큰은 **채도**로 구분해 색상 자체를 새로 쓰지 않는다.

## 4-4. 해금 진행 노출

| 위치 | 내용 |
|---|---|

| 런 중 HUD | **표시하지 않는다** — 전투 중엔 메타 정보가 노이즈다 |

## P1 — 원동력 개통

# 7. 결론

## 한 문장

> **방 구조를 "시드가 정한 레일"에서 "내가 쓴 것이 정하는 지형"으로 바꾸면, 이동이 결정이 되고 런 안에 주도권이 생긴다.**
> **해금이 생기면 죽음이 진전이 되고 런 사이에 원동력이 생긴다.**
> 둘의 결합점은 **"시작 토큰 구성을 바꾸는 해금"** 이다 — 메타가 파워가 아니라 **런의 형태**를 바꾸므로, 해금이 늘어도 런 내 선택의 무게가 죽지 않는다.
